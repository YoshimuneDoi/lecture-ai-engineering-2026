### 3. 正式な定義との比較

比較の基準は、公式用語集の区分と意味、および「どれか1つに取り組めば、その回の宿題は完了」という条件とした。同じ質問についてA・B各3回答を比較した。Bでは1回の503を含む4試行で3回答を得ており、3回すべて成功した実験とは区別する。

| 試行 | 回答で使われた主な区分 | 公式資料と比べた結果 |
|---|---|---|
| A1 | 基礎・初級／応用・中級／発展・上級 | 第2区分の正式名「実装」がなく、内容も一般的な難易度分類。講座固有の完了条件は特定していない |
| A2 | 基礎・ベーシック／応用・スタンダード／発展・アドバンス | 「自力でコードを書く」など意味が一部近い説明はあるが、正式区分の再現ではない。一般例として最低限レベル1〜2などにも言及 |
| A3 | 基礎／応用／挑戦 | 第2・第3区分の名前が異なる。「1つ選んで提出」は複数の可能な規則の一例で、講座の実際の条件を確定した回答ではない |
| B2 | 体験する・使う／使いこなす・改善する／構築する・実装する | AI活用の習熟段階に置き換わっている。「実装」は第3段階の説明に現れ、講座の第2区分を特定したものではない。完了条件はない |
| B3 | 基礎知識／応用・活用／専門・構築 | 習熟度指標の一般例。第1区分に「基礎」が含まれるが、正式な3区分と各意味を正確に示していない。完了条件はない |
| B4 | 基礎・基本／応用・実践／発展・統合 | 講義内容の確認やコードの工夫という意味は一部近いが、第2区分の正式名「実装」を示していない。技術の深さや個人・チームの関わり方という別解釈も提示。講座固有の完了条件はない |
| A4（追加） | 難易度別、プロンプトの段階、システムの階層という複数仮説 | 教材を直接参照できないと述べ、候補を広げている。講座の正式な区分と完了条件は特定できていない |

**同じモデル内の変化：** Aでは3番目の区分が「発展」から「挑戦」に変わり、説明例や提出規則の候補も変化した。B2・B3はAIの利用・活用・構築という段階を中心に説明し、B4は「基礎・基本／応用・実践／発展・統合」という課題難易度を中心に説明した。B4は技術の深さや個人・チームでの学習という別の解釈にも言及しており、同じ質問でも説明の枠組みが変わった。

**モデル間の違い：** Aの主要3回答は宿題の難易度分類を中心にしていた。B2・B3ではAI活用段階の説明が目立ったが、B4はAと近い難易度分類も用いた。追加回答から、Bの内部でも説明の枠組みが変わることが分かった。今回の少数の回答では、モデル間の固定した違いと実行ごとの揺らぎを切り分けられず、一般的な性能順位は判断できない。

**不確実性の表現：** A・Bとも「一般的」「講座によって異なる」などの留保や、資料確認を促す記述があった。そのため、全回答を「講座の規則を断定して間違えた」と一括しない。一方、留保があっても、求められた講座固有の定義を確認できていないという課題は残る。

### 4. エラーと保存方法への対応

**503エラー：** X1とB1で「モデルが混み合っています（503）。少し待ってから再実行してください。」と表示された。これは講座プログラムのエラー用メッセージであり、このログだけから詳細な原因、APIキーの問題、利用上限超過、サービス全体の障害を断定することはできない。回答が生成された記録がないので、内容の誤答とは分けて扱った。

**手動中断：** X2では応答待ち中にCtrl+Cを押し、`KeyboardInterrupt` と終了時の `BrokenPipeError` が表示された。2回目の503や90秒の時間切れとは扱わない。中断しなかった場合のサーバー側の結果は不明である。

**ログの上書き：** A2とA3で同じ `model_a_2.txt` を `tee` の追記指定なしで使ったため、後の出力が前の出力を上書きした。端末の原ログには両方が残っていたので、実行順に別名で復元した。再実行した新しい回答への置き換えは行っていない。

| 実行順 | 元の保存先 | 今回の保存先 |
|---|---|---|
| A1 | `model_a_1.txt` | `a_run01.txt` |
| A2 | `model_a_2.txt`（後に上書き） | `a_run02.txt`（端末ログから復元） |
| A3 | `model_a_2.txt` | `a_run03.txt` |
| A4 | `model_a_3.txt` | `a_run04.txt` |

**追記と重複の照合：** 後から添付した `model_b_alt_3.txt` には、同じモデル名・質問の出力が2件あった。1件目（1〜32行目）は既存のB3とバイト単位で完全一致し、2件目（33〜71行目）は別の回答だった。1件目を二重に数えず、2件目だけをB4として抽出した。元ファイルは両方を含む状態で保存している。ファイル名の末尾「3」だけでは試行回数を判断できないことも確認できた。

Bでは `python -u`、`2>&1`、`tee -a` を用い、表示のバッファリングを抑えて、標準エラーも含めて追記保存した。`set -o pipefail` も実行した。ただし、終了コードの数値自体は記録していない。

### 5. 学んだことと今後の改善

1. **質問と評価基準をそろえる。** 正式区分・意味・完了条件を確認すれば、長さや自然さだけで回答を評価せずに済む。
2. **回答内容と通信の成否を分ける。** 503や中断は回答取得の問題として記録し、得られた文章の正誤と混ぜない。
3. **元ログを残し、重複を照合する。** ファイル名を試行順に分け、コマンドと出力の対応を残す。上書きされた回答は原ログから復元した。追記ファイルの既存回答は完全一致を確認して重複計上を避けた。
4. **実測していない数値を埋めない。** トークン数、応答時間、試行日時・間隔は未取得と記載する。設定した90秒と、実際の応答時間を区別する。
5. **今後の改善案：** 事前に試行回数・失敗時の打切り条件・保存名を決め、日時と終了コードを自動記録する。また、講座資料を入力に含めた場合の変化を調べたい。これらは今回実施済みの結果ではない。
